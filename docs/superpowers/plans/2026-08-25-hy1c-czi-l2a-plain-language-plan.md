# HY-1C CZI L2A 接下来怎么做（大白话版）

## 现在已经有什么

我们已经把“认识这类数据”的部分做好了。

- 系统知道 HY-1C CZI L2A 文件里哪些位置是 460、560、650、825 四个波段。
- 系统知道怎样把文件里的原始数字换成可用数值，哪些无效值要丢掉，哪些质量标志代表陆地、云、强太阳耀斑等应当遮掉的像元。
- 系统知道一条 L2A 任务应该经过哪几个步骤，也知道用户可以选择是否额外做特征、彩色融合和显著性图。
- 这些基础内容已经在 `main` 分支

但现在还不能把一个真实 L2A 数据包从上传一直处理到用户下载。缺的不是“再识别一个波段”，而是把每一步的文件交接、真正处理、接口和页面连起来。

## 总目标

用户在页面上上传一个 HY-1C CZI L2A 数据包，选择波段、范围和分辨率，点击处理。系统后台按顺序完成处理，页面能看见进度；结束后用户能下载标准 COG 影像、元数据，以及可选的融合图、特征结果或显著性结果。

中间文件只给系统自己用，用户看不到，也不能通过接口或 Worker 路径越权读取。

## 第一步：先把“上一道工序交给下一道工序”做好

目前 Worker 做完一段处理后，Java 只知道它说“我生成了一个文件”，但没有把这个文件正式收进当前任务自己的目录。下一步 Worker 甚至可能看到不该看到的原始文件。

要改成下面这种方式：

1. 每个阶段事先写清楚：我要什么输入，会产出什么文件。
2. Worker 只在这一次任务的临时目录写文件。
3. Java 检查文件确实存在、大小对不对、SHA-256 哈希对不对、文件名是不是阶段声明的那个。
4. 检查通过后，Java 把它移动到任务专属目录，并记录为正式产物。
5. 下一个阶段只能拿到它声明需要的那几个文件。

可以把它理解为流水线交接：Worker 负责加工，Java 负责验货、入库和发料。Worker 不能自己决定成品放在哪里，也不能去仓库里随便拿料。

这一步完成后，才有可靠的多阶段处理基础。它也是后面所有工作的前提。

## 第二步：把 L2A 的后半段处理真正跑起来

现在已能做“读数值”和“遮掉坏像元”。接下来继续完成：

1. 根据经纬度，把卫星条带数据投到一个规则网格上。
2. 用户选了范围时，按该范围裁剪；没选就原样通过。
3. 写出标准 COG 文件，带上坐标系、分辨率、四个波段名称、NoData 和处理记录。

标准流程就是：

```text
检查数据包
  -> 读取并换算波段数值
  -> 屏蔽云、陆地等不可靠像元
  -> 根据经纬度投影成规则图像
  -> 按用户范围裁剪（可选）
  -> 输出标准 COG 和说明 JSON
```

处理真实大文件时要分块读，不能把所有波段、经纬度和质量标志一次性塞进内存。这里也不要额外发明 L1B 定标公式，因为当前输入是 L2A 产品，现有 `Rrc` 变量应按已审查的定义使用。

## 第三步：把三种附加算法接到标准结果后面

这三种算法可以实现，但它们不是所有卫星、所有产品都天然适用的“通用科学结论”。目前的定位是可选的基础产品：

- **特征提取**：输出统计值、梯度、局部方差等，帮助看纹理和变化。
- **多波段融合**：把用户选的红、绿、蓝波段拉伸组合成便于浏览的彩色图。
- **显著性检测**：从一个选择的波段找出与周围反差较大的区域，输出分数图和二值掩膜。

它们都只读取标准化后的影像，单独输出新文件，绝不能改写标准 COG。页面也应明确把融合图、特征图、显著性图作为附加/浏览结果，而不是把它们说成海洋业务反演或分类结论。

## 第四步：固定后端和前端之间说什么

前端只需要提交用户真正能理解的内容：选哪些波段、用什么投影、分辨率多少、是否裁剪、是否开启三种附加结果。

后端需要返回：

- 当前任务是否在排队、处理中、成功、失败或取消。
- 每一步目前做到哪里；失败时的错误码和错误信息。
- 哪些最终文件可以下载，文件大小是多少。

后端绝不把服务器本地路径告诉浏览器。浏览器也不传临时目录、输出目录、质量位编号、阶段依赖这些内部信息。

接口稳定以后，前端开发就不需要猜后端的内部实现，双方可以独立开发。

## 第五步：改前端页面

目前页面偏向 GF-6 WFV。需要改成“选择产品模板”的方式，让 GF-6 和 HY-1C 都能共存。

当用户选择 HY-1C CZI L2A 时：

1. 页面提示上传三个文件角色：L2A HDF5、XML 元数据、JPG 浏览图。
2. 页面显示波段、目标坐标系、分辨率、裁剪范围和三个可选算法的设置。
3. 处理开始后显示六个主步骤的中文进度。
4. 失败的阶段可以重试；成功后只显示最终文件的下载按钮和 ZIP 下载。

中间文件不要出现在页面上，避免用户误把内部临时数据当成正式结果。

## 第六步：拿真实数据做一次完整验收

使用已有的真实 HY-1C CZI L2A 样例，完成一次从上传到下载的流程。

验收时重点看四件事：

1. 结果对不对：COG 有正确投影、四个波段名、NoData，文件能被 GDAL 正常读取。
2. 流程对不对：每个阶段只拿到自己该拿的输入；中间文件被正确交接。
3. 安全对不对：接口和日志没有泄露真实数据在服务器上的路径；用户只能下载最终文件。
4. 页面通不通：能建任务、看进度、看到失败原因、下载 COG 和 ZIP。

如果开启融合或显著性，还要确认它们只多产生附加结果，标准 COG 本身不变。

## 推荐的交付顺序

先完成第一步和第二步，再开始第三步到第五步，最后做第六步验收。原因很简单：没有可靠的文件交接，后面做得再漂亮也会在真实任务里断掉；没有稳定接口，前端会反复返工。

完成一项就单独提交一次代码，至少拆成：阶段产物交接、L2A 后半段处理、后端 API、前端页面、真实数据验收。这样出现问题时能快速知道是哪一层出了问题。
